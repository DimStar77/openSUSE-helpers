🦎 Geckopit User Guide: Packaging Workflow Cockpit

Welcome to the Geckopit User Guide. Geckopit is a graphical cockpit and command-line tool for openSUSE packagers maintaining multi-branch upstream repositories (such as GNOME:Factory and GNOME:Next).

This guide is organized by packaging tasks. Each section provides dedicated, step-by-step instructions for both the Desktop Cockpit (GUI) and the Terminal Suite (CLI).

💡 First time packaging on this machine? See the Appendix: Packaging Environment Setup & Onboarding to verify or configure Git identity, SSH keys, OBS, and Gitea in under a minute.

🚀 1. Overview & Cockpit Layout

Geckopit provides two complementary interfaces:

  • Cockpit GUI (geckopit): A responsive desktop application with real-time multi-branch tracking, embedded terminal tabs, 1-click update/merge/PR actions, and syntax-highlighted code diffing.
  • Terminal CLI (geckopit-cli): A fast command-line suite for single-package inspection, batch audits, headless upgrades, and whitespace-sanitized commits.

Figure 1: Full Cockpit Layout Overview

The Cockpit is organized into four main functional regions:

  1. HeaderBar: Switch workspace profiles, run background multi-workspace sync, and adjust preferences.
  2. Package Master Sidebar: Search bar, linked filter toolbar, and real-time package list with status badges.
  3. Detail Workspace: Dual pipeline cards (Stable and Unstable), inline Meson drift repair, and code-diff viewer.
  4. Embedded Console Drawer: Multi-tab terminal drawer with draggable tabs, font zooming, and auto-scroll pause.

🗂️ Workspace Profiles & Pipeline Modes

Geckopit manages multiple independent packaging checkouts via Workspace Profiles (stored in ~/.config/geckopit.json).

  • Switching Profiles: Select a profile from the HeaderBar dropdown (e.g. GNOME, X11, Python). Switching profiles instantly reloads package checkouts, isolates background scan threads (scan_generation), and protects against UI lockups or stale data bleeding.
  • Workspace Profile Manager (⚙️ Preferences):
  • Click the gear icon (preferences-system-symbolic) in the HeaderBar to configure profiles.
  • Adding New Profiles: Click ➕ Add New to create a profile without modifying or overwriting existing checkouts.
  • Zero-Click Onboarding: When selecting a workspace directory, Geckopit inspects .git/worktrees on disk. If a linked worktree exists, it automatically pre-fills stable and unstable paths and branch names.
  • Dual-Pipeline vs Single-Pipeline Mode:
    • Dual-Pipeline: Configured with both factory and next paths. Both Stable and Unstable pipeline cards are active.
    • Single-Pipeline / Portfolio Mode: For standalone maintenance or multi-project portfolios, leave the Unstable branch path empty. Geckopit automatically streamlines the interface: the Unstable card is hidden, branch forwarding tracks are dimmed, and the cockpit focuses 100% on package state, upstream releases, and pool submissions.
  • Maintainer Portfolio Trees & Hybrid Packaging (Git + OSC):

  • Maintainers managing personal packages across multiple OBS devel projects and Gitea organizations can point Geckopit at a single container directory (e.g. ~/packaging): text ~/packaging/ ├── dimstar/ (Git-managed personal packages) │ ├── meson/ [Git] │ └── vlc/ [Git] ├── games/ (OBS 'games' project checkout) │ ├── toycars/ [OSC] │ └── xmoto/ [OSC] └── graphics/ (OBS 'graphics' project checkout) └── shotwell/ [OSC]

  • Boundary-Aware Discovery: Geckopit automatically discovers packages up to 2 levels deep, stopping recursion at package boundaries (.spec with .git or .osc).

  • Visual Category Subtitles: Packages display their category / organization tag in the sidebar: 📂 dimstar / vlc, 📂 games / toycars.
  • Hybrid VCS Support: OSC packages display their project origin in the subtitle (e.g. OSC: games) and adapt card actions to 💾 osc ci when modified.
  • Sub-Millisecond Status Checks: Local modifications are verified via in-Python XML inspection in 0.16 ms (eliminating CLI subshell lag).
  • Safe Workspace Sync: Running geckopit-cli --sync synchronizes all nested Git checkouts in parallel while safely leaving OSC directories untouched.
  • Background Concurrency: Adjust worker pool size (Max Concurrent Scans, from 5 to 50 threads).
  • Ignored Versions Sub-Panel: Review, add, or remove stagnant upstream release tags ignored across your packages.

🎯 2. Finding What Needs Attention & Browsing

Understanding Status Badges

Badge Meaning Action Recommended
Local -N Local checkout is behind origin by N commits. Fast-forward pull from origin.
Local +N Local checkout has unpushed commits on disk. Push commits to origin.
Update Av. Upstream has released a newer version on release-monitoring.org. Run package upgrade.
Fwd. Developmental commits on next ready to promote to factory. Review diff and create PR.
Pool Ahead Local Factory has commits waiting to be submitted to Gitea pool. Run pool submission.
Pool Behind Central Gitea pool has updates that need to be pulled down. Pull down pool updates into Factory.
No Pool Package is not hosted in central Gitea pool. Informational (suppressed from default sync table).
Conflict Automated sync encountered git merge conflicts. Resolve in console drawer shell.
SR #N Active OBS submit request under review in Factory staging (or awaiting pool sync). Inspect in OBS (osc request show N) or wait for sync.

🖥️ In the Cockpit (GUI)

The linked toolbar at the top of the sidebar lets you switch between focused work queues and full catalog browsing:

Figure 2: Quick Filter Tracks & Action Queue

  • Action Queue Mode (⚠️ Needs ON — Default):
  • Only packages requiring maintainer attention are displayed.
  • Click one or more track buttons (📡 Pool, 🟢 Stable, 🟠 Unst., 🔀 Fwd.) to narrow your work queue down to that specific task set (or their combined union).
  • If no track buttons are active, all actionable packages across all tracks are shown.
  • Catalog Browse Mode (⚠️ Needs OFF):
  • Toggling ⚠️ Needs off switches the sidebar to browse all packages across the checkout tree.
  • The four track filter buttons are automatically dimmed (sensitive=False), and track shortcuts (Ctrl+2..Ctrl+5) are ignored.
  • Your previous track selections are remembered and immediately restored when you toggle ⚠️ Needs back on.
  • Ignoring Stagnant Versions:
  • If an upstream project has an abandoned pre-release tag cluttering your queue, hold Ctrl + Alt and right-click directly on the version label in the Unstable Pipeline card.
  • Select 🚫 Ignore Version {Version}. The package will slide out of your filtered sidebar list. (Repeat and click 🔄 Unignore to restore).

🔍 Extended Filtering Capabilities & Query Tokens

Geckopit provides a three-tiered filtering architecture combining instant toolbar tracks, rich search query tokens, and a visual advanced filters popover:

Figure 2b: Advanced Filters Popover (Ctrl + Shift + F)

1. Quick Filter Tracks Toolbar (Ctrl + 1 .. 5)

  • ⚠️ Needs (Ctrl + 1): Toggles between focused Action Queue mode and full catalog Browse mode.
  • 📡 Pool (Ctrl + 2): Filters for central pool synchronization tasks (packages behind pool, unsubmitted commits, or missing from pool).
  • 🟢 Stable (Ctrl + 3): Filters for stable pipeline actions (factory upstream bumps, unpushed commits, unpulled remote commits, or local modifications).
  • 🟠 Unst. (Ctrl + 4): Filters for unstable pipeline actions (next upstream bumps, unpushed commits, unpulled remote commits, or local modifications).
  • 🔀 Fwd. (Ctrl + 5): Filters for pre-release forwarding readiness (next ahead of factory ready to merge or create PR).
  • Multi-Track Unions: Click multiple track buttons simultaneously (e.g. 📡 Pool + 🔀 Fwd.) to display packages matching any of the selected tracks.

2. Search by Query Tokens (@token or is:token)

Type tokens directly into the search bar, with or without package name fragments:

Category Query Token Description
Worktree State @dirty (or @modified, @uncommitted, @untracked) Packages with modified or untracked local files on disk.
@unpushed (or @push, @ahead) Packages with local commits waiting to be pushed to remote origin.
@pull (or @behind) Packages behind remote tracking branch (git pull needed).
@conflict (or @conflicts, @merge-conflict) Packages with unresolved git merge conflicts.
Branch Sync @diverged Packages where next and factory branches have diverged history.
@catchup (or @merge) Packages where next is behind factory requiring a catch-up merge.
@promote (or @fwd, @forward) Packages where next is ahead of factory without an open PR.
Packaging & Pool @pr (or @prs, @pullrequest) Packages with active Gitea Pull Requests or pending OBS Submit Requests.
@nopr (or @unsubmitted) Packages forwardable from next to factory without an open PR.
@pool Packages that are ahead or behind the central openSUSE Gitea pool.
@nopool (or @not-in-pool) Packages not hosted in the central Gitea pool.
@outdated (or @supersede, @outdated-sr) Packages with outdated pending submit requests ready to supersede via osc sr.
@sr (or @pending-sr) Packages with active pending or accepted OBS submit requests in openSUSE:Factory.
@update (or @updates, @needs-update) Packages with newer upstream releases on release-monitoring.org.
  • Compound Queries: Combine package names with multiple tokens freely (e.g. gnome @pr, gtk @dirty, lib @update @pool).
  • Instant Keyboard Confirmation: Press / or Ctrl + P to jump to the search bar. Press Enter or Down to immediately confirm your query and focus the first matching package in the list.
  • Selection Lock Guard: When typing or switching filter tracks, the currently selected package remains pinned and immune to filter removal, ensuring your active workspace never slides out of view.

3. Visual Advanced Filters Popover (Ctrl + Shift + F)

Click the settings icon (preferences-other-symbolic) next to the search bar (or press Ctrl + Shift + F) to open the filter menu:

  • Toggle checkboxes across Worktree State, Branch Synchronization, and Packaging & Pool categories.
  • The button illuminates with a blue accent badge (.suggested-action) whenever popover filters are active.
  • Click Reset to clear all active popover filters at once.

🛡️ CLI Option Validation & Typo Suggestions

geckopit-cli strictly validates all leading - arguments against KNOWN_OPTIONS. If you mistype a flag (e.g. geckopit-cli --c or geckopit-cli --comit), Geckopit avoids accidental fallthrough to the default dashboard or sync table, halting immediately with exit code 1 and providing intelligent suggestions:

[Error] Unrecognized option '--comit'. Did you mean '--commit'?
See 'geckopit-cli --help' for available options.

⚙️ 3. Upgrading a Package to a New Upstream Release

When an upstream project releases a new version, Geckopit automates the entire upgrade: fetching new sources ➔ bumping the version in .spec ➔ extracting upstream release notes ➔ wrapping changelog bullets at standard 79 columns ➔ dropping merged patches ➔ checking for Meson dependency bumps.

Geckopit automatically adapts to how the package is maintained:

  • Service-managed packages (_service): Fetches upstream Git commits, drops merged patches, and updates packaging metadata.
  • Direct tarball packages (.spec): Reads downloaded source archives, extracts changelogs, and updates spec files.

🖥️ In the Cockpit (GUI)

Figure 3: Dual Pipeline Action Cards & Dynamic Upgrade Button

  1. Select a package showing the orange Update Av. badge (e.g. zenity or libgsf).
  2. In the Pipeline card, review the version comparison (e.g. 4.2.0 ➔ 4.2.2).
  3. Click the dynamic update button (e.g. Update Next to 4.2.2 or Update Factory to 4.2.2).
  4. An embedded terminal tab opens in the bottom drawer, executing the upgrade engine, bumping the spec version, wrapping the .changes entry at 79 columns, and dropping merged patches.
  5. Upon completion, the update button transitions to Up-To-Date and illuminates the Push button.
  6. Click Push to push your packaging commits to origin.

Stable Pipeline Card Action Buttons:

  • 📥 Pull: Fast-forward pull remote commits from origin into your local stable checkout.
  • 📤 Push: Push committed packaging updates to remote origin.
  • 📥 Pull Pool: Merge upstream updates down from the central Gitea pool into your stable branch.
  • 📤 Submit Pool: Submit package changes from factory to openSUSE:Factory via osc sr, with automated pre-flight worktree verification, changelog diff extraction, and pending SR detection.
  • ⚙️ Run SCM Update: Execute automated package upgrade engine.
  • 🖥️ Terminal (factory): Launch a dedicated console drawer tab navigated to the package's stable worktree.

💻 In the Terminal (CLI)

Run geckopit-cli --upgrade directly inside the package directory:

# Upgrade package to target revision (default: @PARENT_TAG@)
geckopit-cli --upgrade 4.2.2

# Or simulate the entire upgrade without modifying any files (dry-run)
geckopit-cli --upgrade 4.2.2 --dry-run

🔍 Sequential Patch Pre-Flight Verification (--check-patches)

When maintaining packages with multiple downstream patches, verifying whether patches apply cleanly against a newly downloaded archive or rebased tree previously required manual quilt setup, extracting large archives, and managing quilt stacks.

Geckopit provides a built-in sequential patch verification engine:

# Verify downstream patches against the upstream source in strict .spec order
geckopit-cli --check-patches

# Or run against a specific package from anywhere
geckopit-cli webkitgtk --check-patches

# Display detailed SLE patch conflict traces beneath the summary
geckopit-cli --check-patches --sle
geckopit-cli --check-patches --verbose

# Interactively rebase a failing downstream patch in-place without quilt
geckopit-cli --rebase-patch

# Target a specific patch by name
geckopit-cli --rebase-patch g-s-d-skip-donation.patch

# Rebase failing SLE patches (or auto-targets SLE if openSUSE patches are clean)
geckopit-cli --rebase-patch --sle

# Or drop into a scratch subshell instead of launching an editor
geckopit-cli --rebase-patch --shell

🔧 Interactive Patch Rebaser (--rebase-patch)

When a patch fails due to upstream refactoring or shifted context, running quilt setup creates messy .pc directories, unpacks gigabytes of archives, and requires manual copying and directory deletions.

geckopit-cli --rebase-patch replaces the entire quilt workflow with a native, zero-setup Git scratch workspace:

  • Auto-Targeting (openSUSE & SLE): Automatically detects the first failing openSUSE patch. If all openSUSE patches apply cleanly, it automatically falls through to target failing SLE patches (or explicitly via --sle).
  • Preceding Patch Replay: Sets up an ephemeral Git repository in /tmp, replaying preceding patches in .spec declaration order. For SLE patches, all openSUSE patches are replayed first, followed by any preceding clean SLE patches.
  • Reject Triage: Applies the target patch with rejected hunks (.rej) and displays them in full color in the terminal.
  • Git-Identical Editor Resolution: Launches your editor following Git's exact 5-tier resolution order ($GIT_EDITOR ➔ core.editor ➔ $VISUAL ➔ $EDITOR ➔ vi/vim), opening vim -O file.c file.c.rej side-by-side when using Vim. If --shell is supplied, drops into an interactive scratch subshell.
  • Multi-File Sequential Walkthrough: When a patch touches multiple failing files, Geckopit walks through each failing file one-by-one ([1/N], [2/N]), keeping exactly 2 clean vertical splits open at any time without overflowing the screen.
  • In-Place Update & Changelog Recording: Automatically captures git diff, preserves the original patch header / description / bug references (bsc#...), updates the patch file on disk, records - Rebase {patch}. in *.changes (cleanly appending to an in-flight upgrade entry or invoking osc vc), runs geckopit-cli --check-patches, and cleans up all scratch files.
  • Already-Merged Intelligence: If the patch changes are already present upstream in reverse, it alerts you immediately that the patch has been merged and can be dropped from the .spec file.

Key Verification Principles:

  • Sequential Dependency Chaining: Unlike isolated file checks, patches are applied sequentially (Patch0 ➔ Patch1 ➔ Patch2), allowing dependent patches to chain on top of earlier modifications.
  • Halt at First Failure: Like quilt, the engine immediately halts at the first failing openSUSE patch to prevent misleading cascade failures.
  • Multi-Archive & Subproject Resolution: Resolves primary source archives strictly from .spec declarations (Source0 / Source) and macro expansions rather than filesystem timestamps. If downstream patches target files inside subprojects or vendor tarballs (e.g. subprojects/gvc in gnome-shell), matching members from declared secondary archives (Source1, Source2) are automatically unpacked into target directories before testing patches.

  • SLE-Only Patch Intelligence & Quiet Summary: Failure modes are differentiated into genuine code conflicts (conflict) vs missing auxiliary files (missing_file). Distro-specific SLE patches (Patch1000+, %if !0%{?is_opensuse}, %if 0%{?sle_version}) are evaluated quietly in a compact summary line without halting the main pre-flight check or blocking openSUSE upgrades: text 🎉 All 4 openSUSE downstream patch(es) applied cleanly in sequence! ℹ️ SLE status: 4/10 apply cleanly (6 conflict against new upstream). Pass --sle or --verbose to view the exact failing files and diff traces for SLE patches.

  • Unconditional SLE-Tagged Safety: Patches preceded by # PATCH-*-SLE comments that are applied unconditionally across openSUSE in %prep remain classified as openSUSE patches and are verified in the primary blocking check.

  • Resume After Rebase: When a patch fails, simply edit and fix the patch in your editor, then re-run geckopit-cli --check-patches. The engine verifies in ~0.1s without needing directory teardowns, .pc deletions, or manual quilt resets!
  • Automated Upgrade Integration: geckopit-cli --upgrade automatically triggers this pre-flight check after dropping merged patches, immediately alerting you if any remaining downstream patch needs rebasing before you commit.

🔧 4. Auditing & Fixing Build Dependency Drift (Meson, CMake, Autotools, Python)

Upstream projects often bump minimum dependency constraints in meson.build, CMakeLists.txt, configure.ac, or pyproject.toml without maintainers noticing. Geckopit inspects the .spec file to identify active build systems (supporting declarative BuildSystem: tags, build invocation macros, %pyproject_wheel, and BuildRequires), and audits upstream declarations against your .spec BuildRequires: (including %{python_module ...}).

🖥️ In the Cockpit (GUI)

  1. When a package has dependency drift, a compact yellow warning banner appears on the detail card: text ⚠️ Meson Drift: 1 unversioned [🔧 Fix in .spec]

  2. Hover over the banner or right-click to view the exact requirements.

  3. Click 🔧 Fix in .spec.
  4. Geckopit immediately updates the BuildRequires: declaration in the .spec file (or updates the corresponding %define macro if defined), appends the standard changelog entry (- Update version dependencies according to meson.build.), and refreshes the view.

💻 In the Terminal (CLI)

Audit and fix dependencies directly from your shell:

# Audit dependencies against .spec BuildRequires
geckopit-cli --audit-deps

# Automatically update .spec BuildRequires / %define macros and record changelog
geckopit-cli --fix-deps

Sample Output (--audit-deps):

=> Auditing Meson dependencies for 'zenity'...

⚠️  Meson Dependency Drift Detected:
   • pkgconfig(libadwaita-1) >= 1.2 (spec currently has unversioned BuildRequires)

💡 Recommended Action: Update BuildRequires in zenity.spec to match upstream requirements.

  6. Creating Pull Requests: Click Create Pull Request on the Pipeline card:
  7. Smart Changelog PR Prefiller: Geckopit automatically constructs the PR title (e.g. Update to version 4.2.2) and extracts the newly added .changes entries directly into the PR description body.

📥 Managing & Merging Pull Requests (CLI)

Maintainers routinely review and incorporate contributions from external submitters or check open PR status across their workspace:

# List open PRs for the current package (or workspace-wide overview from the root)
geckopit-cli --list-prs

# List open PRs for a specific package from anywhere
geckopit-cli webkitgtk --list-prs

# Fetch and merge a contributor PR onto your active branch HEAD
geckopit-cli --merge-pr 24

# Merge and squash multi-commit PRs into a single atomic commit
geckopit-cli --merge-pr 24 --squash

# Stage PR changes without auto-committing (for review or manual touch-ups)
geckopit-cli --merge-pr 24 --no-commit

Key PR Merge Capabilities:

  • Direct Origin Fetch: Fetches pull/<ID>/head directly from origin without needing contributor fork URLs or commit SHAs.
  • Fast-Forward & Signature Preservation: When HEAD is an ancestor of the PR (such as promoting next ➔ factory or applying a clean contributor branch), merges using git merge --ff-only, preserving 100% of original commit hashes, attribution, and existing GPG signatures without prompting for maintainer keys. For non-fast-forward merges, creates clean merge commits with PR commits intact as Parent 2 in Git history.
  • Locale-Independent Changelog Engine: Parses and redates openSUSE .changes headers (LC_ALL=POSIX date) using explicit English weekday and month tables, ensuring date ordering validation and redated headers are 100% immune to regional desktop locale settings (e.g. de_CH.UTF-8).
  • Spec Collision Guard: Scans .spec files for duplicate Patch<N>: numbers (e.g. conflicting Patch2: additions) and safely halts before committing, leaving changes staged for maintainer review with git commit -c FETCH_HEAD.
  • Forwarded PR & Group Intelligence: --list-prs queries _ObsPrj to report whether a package PR is forwarded individually or bundled into a multi-package release group (e.g. pr-manage combine).

📤 Central Pool Submissions & Pending Request Audit

When developmental updates on factory are ready for integration into the distribution, submit them to openSUSE:Factory with automated pending request detection:

# Workspace-wide audit: Identify which packages truly need submission to openSUSE:Factory
geckopit-cli --check-pool

# Inspect pending submit requests for an individual package
geckopit-cli libnotify --check-pool

# Submit package changes to openSUSE:Factory (dry-run simulation)
geckopit-cli libnotify --submit-pool --dry-run

# Submit package changes with auto-extracted .changes description
geckopit-cli libnotify --submit-pool

# Submit with a custom message
geckopit-cli libnotify --submit-pool -m "Update to version 0.8.9"

# Interactively submit all unsubmitted workspace packages at once
geckopit-cli --submit-pool --all

Key Submission Capabilities:

  • Sub-2-Second Distribution Audit: Queries the project-wide OBS submit request collection (/request?view=collection&project=openSUSE:Factory&states=review,new&types=submit) in ~1.8 seconds total, cross-referencing all 500+ packages in memory.
  • Existing SR Guard: Prevents redundant submissions when a request is already under evaluation in Factory staging (e.g. ⏳ Pending SR #1385454 (review)).
  • Sync Gap Intelligence: Audits recently accepted submit requests within a sliding window to catch packages accepted in OBS that have not yet finished backend mirroring to src.opensuse.org/pool/<pkg>.git.
  • Safe Workspace Crossover: When invoked from an unstable worktree (such as GNOME:Next on next), Geckopit automatically notifies you and routes the submission to your configured stable checkout (GNOME on factory), preventing developmental code from leaking into Factory.
  • Future Git-Pool Readiness: Inspects target project meta for <scmsync> tags, automatically guiding maintainers toward Gitea Pull Requests once openSUSE:Factory migrates to Git.

🔄 6. Synchronizing Multi-Branch Workspaces

Synchronize your local workspace trees with remote tracking branches across all profile checkouts.

🖥️ In the Cockpit (GUI)

Figure 6: Embedded Multi-Tab Console Drawer

  1. Click the 🔄 Sync Workspace button in the HeaderBar.
  2. Geckopit synchronizes all package checkouts in the background. A spinner animates on the button while working.
  3. The console drawer remains hidden if the sync completes cleanly.
  4. Notifications:

💻 In the Terminal (CLI)

Run workspace synchronization from the command line:

# Parallel fast-forward workspace synchronization
geckopit-cli --sync

# Fetch remote objects only without merging
geckopit-cli --fetch

💾 7. Committing Packaging Changes & Whitespace Sanitization

Geckopit includes a modernized packaging commit helper (replacing legacy gc.sh). It ensures clean Git history by sanitizing trailing whitespace and preventing review artifacts from being accidentally committed.

🖥️ In the Cockpit (GUI)

  • Each pipeline card provides dedicated one-click terminal launchers:
  • 🖥️ Terminal (factory): Launches an embedded console drawer tab navigated to the package's local stable worktree.
  • 🖥️ Terminal (next): Launches an embedded console drawer tab navigated to the package's local unstable worktree.
  • Review your working tree changes and run your packaging commit directly in the drawer.

💻 In the Terminal (CLI)

Run geckopit-cli --commit inside any package directory:

# Stages packaging files, strips trailing whitespace, and pre-fills $EDITOR with .changes diff
geckopit-cli --commit

# Commit without opening an interactive editor (uses .changes diff directly)
geckopit-cli --commit --no-edit

Defensive Protections:

  • Automatically strips trailing whitespace from modified .spec, .changes, and packaging files before staging.
  • Stages only packaging files and source services, ignoring untracked build artifacts, cloned upstream directories, and temporary review logs.
  • Extracts newly added entries from *.changes and pre-populates your $EDITOR commit template.

🛠️ Appendix: Packaging Environment Setup & Onboarding

When setting up Geckopit on a new machine, laptop, or Flatpak installation, four developer pillars must be configured to fetch sources, manage pull requests, and commit changes:

  1. Git Identity: Your user.name and user.email used in commit headers.
  2. SSH Authentication: An SSH keypair and authenticated connection to gitea@src.opensuse.org.
  3. Open Build Service (OBS): Your openSUSE credentials in ~/.config/osc/oscrc.
  4. Gitea CLI (tea): An API token configured in ~/.config/tea/config.yml.

In the Cockpit (GUI)

Click the Setup & Verification button (avatar-default-symbolic) on the right side of the HeaderBar to open the interactive setup assistant:

Figure 7: Packaging Environment Setup Dialog

  • Git Identity: Fill in your Full Name and Packaging Email, then click Save.
  • SSH Authentication:
  • If no SSH keys exist, click Generate ed25519 to create a secure keypair automatically.
  • If keys already exist, select your preferred public key from the dropdown list and click the 📋 Copy icon.
  • Click Add Key on Web to open src.opensuse.org/user/settings/keys in your browser and paste the key.
  • Click Test Connection to verify access against gitea@src.opensuse.org without freezing the interface.
  • Open Build Service (OBS):
  • Shows your existing configuration status at a glance.
  • Expand Change Credentials to enter an updated username and password/token, securely saving to ~/.config/osc/oscrc with 0600 permissions.
  • Gitea API Token (tea):
  • Shows your existing configuration status.
  • Click Generate Token on Web to open src.opensuse.org/user/settings/applications.
  • Expand Change API Token, paste your token, and click Save Token to configure ~/.config/tea/config.yml.

In the Terminal (CLI)

Verify or configure your environment headlessly or step-by-step from your terminal:

# 1. Non-destructive readiness check across all 4 pillars
geckopit-cli --check-setup

# 2. Interactive step-by-step onboarding wizard
geckopit-cli --setup

The interactive wizard tests existing settings, offers to generate keys and configurations, displays clickable web links, and automatically validates connections before concluding.
